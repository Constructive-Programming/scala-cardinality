# v1 plan: trustworthy cardinality reports, driven by eo

**Status:** active, consolidated implementation plan.
**Production analyzer baseline:** `726ec431bbcb1b9211622d70d32c2852a9562df7`.

This document consolidates the decisions from the eo reporting work, the reference discussions,
and [PR #10](https://github.com/Constructive-Programming/scala-cardinality/pull/10). It is the
roadmap to maintain as that work proceeds. Older README and PR report snapshots are historical,
not competing definitions of the current baseline. The milestones below do not claim that their
remaining work is already implemented.

## 1. Outcome

Generate a useful, reproducible report for eo's core library, published as
`dev.constructive:cats-eo_3:0.16.0`, then use its actual signatures to improve the general
calculator.

The objective is **correct numbers for each case**, not a higher percentage of rows carrying a
number. An unsupported case must remain explicitly unresolved rather than receive a convenient
finite answer or a guessed infinity.

The working loop is:

1. Select an eo signature and recover everything it can access or capture.
2. Derive its expected count independently of the analyzer.
3. Add a regression containing the relevant source and scope.
4. Implement the general rule, not an exception for that signature.
5. Regenerate the report and explain every changed result.

## 2. Agreed counting contract

### Two different questions

- **Implementation cardinality:** how many observationally distinct, pure, total, parametric
  implementations a signature admits in its accessible environment.
- **Stored-value cardinality:** how many values an instantiated data type holds. The existing
  constructor-input estimates are a separate, approximate view of this question.

For a generic construction signature taking `x: A` and `y: A`, returning `A` has two choices;
constructing a fixed two-field `Pair[A]` has four: `(x, x)`, `(x, y)`, `(y, x)`, `(y, y)`.
That is the intended generic constructor/apply count, not the stored-value cardinality of every
instantiation. `Pair[Int]` has `|Int|² = 2^64` under the fixed-width integer model.

Two available choices need not have different runtime values on every call. The implementations
are distinguishable across admissible inputs. Conversely, two aliases of the same binding do
not create another choice.

### What each report table measures

A report answers the two questions in two tables. The rules each one applies are stated in full
below and in the research notes; this is the map.

**Methods table: implementation cardinality.** One row per method, constructor (`<init>`), given,
extension and inline method. The count is how many observably different pure, total, parametric
bodies fit the signature in its environment.

- Inputs are the parameters, a constructor's included. A parameter of a class type reads that
  class's fields as inputs, so `g(w: Walk)` counts as `g(cur: Any, n: Int)` does.
- The environment adds captures, the receiver's fields (Rule B: the largest space a public
  constructor or, where none is callable, a public factory builds) and abstract members, which are
  capabilities.
- A top type is read in its own arrow: one value in an input, ω in an output, never flipped by
  nesting; containers pass on the place they sit in. Two or more result choices over an argument
  space holding an output top are ω.
- Totality holds: every input needs a result. `first[A](xs: List[A]): A` is 0 (no `A` at `Nil`);
  `f[A](default: A, xs: A*): A` is ω (`default` at length 0, one of n + 1 values at length n).
- `X*` is a possibly empty list. An `inline def` counts as a `def` unless it uses a compile-time
  operation. An opaque type outside its scope is one value.
- The assumptions below apply: no effects (a `var` is a `val`, throwing supplies nothing), the
  closed world, lawful key equality and replayable single-pass reads, and builtin names read by
  their rooted names with equivalent library types counted alike.

**Definitions table: stored-value cardinality.** One row per type (class, case class, enum, alias,
object). The count is how many distinct values a value of the type holds, observed through its
accessible state.

- Products multiply their fields, sums add their cases, an object is one value.
- `Any`, `AnyRef` / `Object` and `Matchable` are ω everywhere, an alias of one included.
  `String`, `BigInt` and recursive types are ω; a function space over a countable type is ε₀.
  Unions keep their sum (`Boolean | AnyRef` is ω + 2).
- A finite capacity prints as the bound `≤2^b`, marked lossy when it holds floating point.

**Constructor and type are measured apart.** A constructor is a method: its parameters are
inputs, so a top in one is one value. The type is a value: a top in its state is ω.
`final class Walk(val cur: Any, val n: Int)` is 2^32 as `Walk.<init>` in the methods table and ω
as `Walk` in the definitions table.

In both tables `?` means the supplied sources do not determine the number, and the reason says
what is missing. A wrong number is worse than `?`.

### Scope and equivalence

- Include parameters, receiver fields, enclosing captures, accessible declarations, projections,
  and callable producers. Do not substitute a bindings-only count for this environment.
- Keep type binders distinct even when they share a spelling or can later be instantiated to the
  same concrete type. Keep term names separate from type names.
- Count modulo the supported observational equivalences: renaming, beta/eta normalization, and
  redundant elimination must not manufacture inhabitants.
- A supplied `step: A => A` and `x: A` admit `x`, `step(x)`, `step(step(x))`, and so on: `ω`.
  Without a starting inhabitant, that cycle supplies no `A`: `0`.
- A known identity is not an unconstrained producer. Repeated calls to it do not establish `ω`.
  Skipping a concrete member requires a justification that its results are already represented;
  parametricity is not a blanket justification for discarding unreadable captures or capabilities.
- Another abstract member can be a supplied capability. The declaration currently being measured
  is **not** its own supplied implementation, including through an inherited/overridden view.
- A numeric answer requires a complete analysis of the relevant environment. If an omitted
  capability might change the result, report `?`, unless irrelevance is established.

### Assumptions and output meanings

The model excludes divergence, effects, mutation-dependent behavior, exceptions, `null`, unsafe
casts, reflection, and unrestricted runtime type/equality tests. It does not certify that an
existing Scala body obeys these assumptions.

In short, the measured code is assumed to have no side effects:

- A `var` is read as a `val` holding the value it was given. No count or reason depends on
  mutability. Scala's typing rules still apply: a `var` is not a stable path.
- Throwing is ignored. A `throw`, or a call that may throw, is neither a value nor an
  implementation, and no count is refused because code might throw. A `Throwable` used as data
  is an ordinary value.
- Effectful members (I/O, `printStackTrace`, `fillInStackTrace`, …) are excluded like the
  universal members.
- So are the members of `scala.Product` and `scala.Equals` (`productArity`, `productElement`,
  `productElementName(s)`, `productIterator`, `productPrefix`, `canEqual`): reflection over a
  value's fields and an equality test. `Product`, `Equals` and `Serializable` are parents that
  declare nothing, so a trait that lists them (scalameta's `Tree`) is read as one that does not.
- An `inline` parameter has its argument's value (boxing aside, which only the excluded universal
  members see), so an `inline def` counts like a `def` unless its body, or an inline method it
  calls, uses a compile-time operation: `inline if` or `inline match`, `scala.compiletime`, quotes
  or splices — or reaches the call site another way (a member a supplied subclass overrides with
  an inline method whose expansion differs, selected on a parameter or `this`, or the `apply` a
  further clause selects on a result; a runtime class reified from a type parameter, by a type
  test or `classOf`; a given left to implicit search; an inline or contextual extension it may
  meet). An abstract `inline def` counts like an abstract `def`, and an implementation through its
  own body. A conversion is typed where the body is written, so it counts unless it is inline and
  its own expansion fails. `transparent` and `inline` parameters do not disqualify a method; a
  `transparent` result stays `?` unless its declared type is a singleton.

The model also assumes a **closed world**: the supplied sources and dependency declarations are the
whole program, and no subclass, override or implementation exists outside them.

- A concrete class no supplied template extends, and a concrete member no supplied template
  overrides, is final. A member a supplied template overrides varies across receivers, so it is a
  capability, as an abstract member is.
- Abstract members stay supplied capabilities (above), and a goal of an abstract template is any
  tuple of them. The implementation being counted is the one new piece of code: it may implement
  an abstract template, but it does not override concrete code.
- Two templates share an instance only where one extends the other or a supplied template extends
  both.
- The closed world settles which templates exist, not what an unresolved name means. An
  unresolved identity, an alias that is not followed, or a scope whose constructions are not
  enumerated keeps its `?`.

Further idealizations, adopted by the owner, stand beside them:

- Key equality is lawful. A `Map` or `Set` uses an equality and hash on its keys that is
  structural and consistent with the key type's value identity, so a `Map[K, V]` is its abstract
  value, a finite partial function, and a `Set[E]` a finite subset. Reading a single-pass
  `Iterator`, `IterableOnce` or byte buffer or stream is an effect, so each is the sequence it
  yields, like a replayable collection (register D36).
- Builtin names are never shadowed by what the sources do not supply. A wildcard import or export
  of an unsupplied namespace, an unsupplied parent or self type, or any other reference the
  analysis cannot resolve, rebinds no name the root imports bind (`Int`, `String`, `Option`,
  `Map`, `Any`, …). An explicit, resolved declaration or import of the name still shadows it. A
  wildcard into the standard library or the JDK binds the names its package declares by their full
  rooted names (`import java.util.*` makes `List` mean `java.util.List`), and a rooted name whose
  values are the same as a modelled type's counts the same while keeping its own identity:
  `java.util.List`, `java.lang.Iterable`, `scala.collection.Seq` and the mutable collections are
  sequences, `java.util.Set` / `collection.Set` sets, `java.util.Map` / `collection.Map` maps,
  `java.lang.Integer` and the other boxes their scalars, `java.util.Optional` an `Option`
  (register D37).
- A top type is read by its place in its own arrow. *Input* is a method's or function's parameter
  or a constructor slot, read by the code receiving it; *output* is a result. Each function type,
  and each method, is read on its own, innermost first: `Any`, `AnyRef` (`Object`), `Matchable` and
  `AnyVal` in that arrow's input hold one value, where the code receiving it observes nothing of
  it, and in its output ω values, where the code that produces it may build any value
  (`def r(b: Boolean): Any` is ω). Nothing flips through nesting: in `f: Any => A` the top is f's
  input (1), in `g: A => Any` g's output (ω). A product, a sum, a sequence, an `Option`, a `Set`'s
  elements and a `Map`'s keys and values take the place they sit in (`Option[Any]`: 2 as an input,
  ω as an output). An input `Set[Any]` is 2 values — its size could tell two apart, and the type
  fixes none (a size known a priori determines the set) — and an output or `val` one ω; a `Map`'s
  keys alike. Arguments are read before the method: the method's count is its result's choices
  over its argument spaces, so where an argument's space holds an output top, two or more choices
  are ω, one stays 1 and none 0 (`def h(g: Unit => Any): Boolean` is ω). A top result is not
  one-valued. `AnyRef` / `Object` and `Matchable` are read exactly as `Any` everywhere, unions
  (`T | AnyRef` is `AnyRef`) and intersections (`T & AnyRef` is `T`) included; `AnyVal` keeps its
  reading. `A <:< Any` (or a reference top) is a proof that carries nothing. An `inline` method's
  top-typed parameter refuses nothing. On the stored-value side `Any`, `AnyRef` / `Object` and
  `Matchable` are ω everywhere, behind an alias too. No count is refused because a top-typed
  position cannot be enumerated (register D38).
- Constructor = a method; type = a value whose accessible state is observed. A constructor (its
  `<init>` row) is counted like any other method: its parameters are inputs, read by the method
  side, so a top in one — spelled or behind an alias, whatever is beside it — is one value, and
  the constructor row never hands a top to the stored-value estimate. The type as a value (its
  definitions row, a top-level `val`) is read by the stored-value side, where a top, aliased or
  not, is ω. `final class Walk(val cur: Any, val n: Int)`: the constructor is 2^32, the type ω.
- A repeated parameter `X*` is a possibly empty list, `Σ_{n≥0} Xⁿ` (`f()` is a call):
  `def first[A](xs: A*): A` is 0, `xs: Any*` as an input ω.
- A conversion, or an inline or contextual extension, is a candidate for a body only where the
  body may find it: (1) in its lexical
  scope, a definition around it or an import, or (2) as a member of an object in the implicit scope
  of a type the body can reach. The types a body can reach are those written in it, those of the
  enclosing signatures, and those of the signatures of every declaration it references or given it
  may summon, repeated until nothing new is added (a fixed point). The implicit scope of those
  types is the companions of their parts and of their supplied base classes, the objects those
  classes are members of, and what those objects extend. In well-typed code every inferred type is
  built from those signatures (a least upper bound is a supertype of the branch types, whose
  companions are reached through their base classes), so the candidates found are all Scala may
  insert or select. A type the reading cannot resolve keeps every candidate. Reading the names a
  type spells by Scala's scoping, without typing, is accepted as precise enough: it can keep a
  candidate Scala would not consider, a refusal, never a wrong count (register D43).

#### Modelling conventions

Three conventions fix what the sources alone leave open (user decisions, 2026-11-05 and
2026-11-10):

- **Compiled result types (rule T).** A member, local or pattern name written without a type has
  the type the compiler gave it, read from the module's own compiled TASTy when the build supplies its classes
  (the sbt and Mill reports do; `cardinalityReportOf` over arbitrary paths does not). It is the
  compiler's answer, so it counts as typed soundly. The type is spelled from `_root_` and written
  into the source before anything reads it, as the closed world writes `final`. The compiler's
  inference is not imitated (user decision, 2026-11-11): a member written without a type refuses
  where no compiled member sits at the same name offset with the same name and span (a stale or
  foreign class, a source that does not compile, `cardinalityReportOf`), where the type has no
  source spelling, and where it is `transparent inline`, whose callers see the expansion (rule X).
  A name typed in its own pattern (`val (a: A, b) = …`) has that type, compiled or written. See
  [compiled-own-types.md](compiled-own-types.md).

- **Receiver constructors (rule B).** The values a receiver's fields hold together — or a
  field-bearing argument's, a final class's record or a sealed summand — are what its *public*
  constructors build, and the space is the **largest** any one public constructor builds, not
  their sum. "Public" is relative to the measured declaration's site: a constructor is public there
  when that site may call it — no modifier, a `private[p]` one inside `p`, a `private` or
  `protected` one inside its class, a `private` one in its companion. Any other is ignored. A class or trait that is itself non-public (`private[p]`, `private`,
  `protected`, nested in a non-public template, or local to a block) has no use site outside its
  scope, so its own restriction is disregarded and its constructors are public. Every secondary
  constructor delegates to the primary, so a public primary builds every field value (the fields
  are any values of their types). Otherwise a public secondary builds at most
  `min(|its parameters|, |the fields|)`. A class (or sealed case) with no constructor the site may
  call is counted by its **public factories** too (user decision, 2026-11-06): the methods and
  `val`s callable from that site that construct it. A definition constructs the class where its
  result — through blocks, local `val`s, `if` and `match` branches — is a direct construction
  (`new C(…)`, a creator application `C(…)`, a case class's `apply`); a branch per case counts for
  each case it builds, and a factory declared to return the family type (`PSVec.of[B](…): PSVec[B]`
  building `Slice`) still constructs the case it builds. A result that calls another method
  (callable from the site or not) whose result constructs the class is read through that method,
  and through one more call: two levels of delegation (user decision, 2026-11-06). The fields are
  only those the site **observes**: a field it may select, or one a member it may call reads
  (directly or through members it may not call); values differing only in fields nothing there
  reads are not told apart, so a class with no observed field is one value, as an opaque type is
  (rule F). Each factory builds at most `min(|its parameters|, |the observed fields|)`, as a
  public secondary does; one that declares the class as its result but whose body is read as no
  construction (a value it was given, a delegation deeper than two calls, an unreadable body)
  counts 1, but a compiled dependency's factory, whose body is not supplied, is not known; one running on a receiver of a class or trait has the receiver as an input too, so its
  space is not known. The measured declaration is no factory of its own result. The class is one
  value of the **largest** space a public secondary or factory builds, not their union: a value is
  one object whichever factory built it, and the factories are no choice between objects (user
  decision, 2026-11-06) — the fields' own as soon as one reaches it, else the largest where every
  space is closed and comparable, else `?` (`receiver space of its public constructors and
  factories not compared`); a sealed case counted this way is one summand of that space, its
  fields not projected. A class with neither a public constructor nor a factory is `?` (`receiver
  has no public constructor: C`). The stored-value side counts a class whose constructor is
  restricted the same way, "public" there meaning unrestricted (a row has no measuring site), from
  the factories of its companion and its body (it reads one source at a time); a class with type
  parameters keeps its fields' product there.
- **Opaque types (rule F).** Outside the scope where its representation is visible, an opaque type
  counts **1**, on the stored-value and the method side alike: it is read as one value (`Unit`),
  and as a type argument it keeps its own nominal identity, as a class does. Inside its scope the
  representation is read as before. So `final case class U(id: Ids.Id)` is 1, `def f(a: Ids.Id,
  b: Ids.Id): Ids.Id` has 1 implementation, and `def get[A](t: Box[A]): A` outside `Box`'s scope
  has 0 (an upper bound `opaque type T[A] <: A` is not read either).

Functor, optic, or other algebraic laws are additional constraints, not implicit consequences
of a signature.

- `Finite(n)`: exact within the stated model, including `0`.
- `Countable` / `ω`: a justified countably infinite family in that model.
- `Unresolved` / `?`: unsupported syntax, incomplete scope/type analysis, or an exhausted
  analysis budget. Neither `ω` nor `ε₀` is an unknown-value fallback.

A `0` is a scope-relative result under these assumptions, not a claim that an unsafe Scala body
cannot be written. Stored-value estimates must not inherit the method counter's exactness claims.

## 3. References and their limits

- Bartosz Milewski,
  [Parametricity: Money for Nothing and Theorems for Free](https://bartoszmilewski.com/2014/09/22/parametricity-money-for-nothing-and-theorems-for-free/):
  why uniform generic implementations are constrained by what they receive and capture.
- Alex Knvl,
  [Counting type inhabitants](https://web.archive.org/web/20181221193229/https://alexknvl.com/posts/counting-type-inhabitants.html):
  observational equivalence, sums/products/exponentials, quantification, empty types, and
  countable families.
- Bertrand Russell, *On Some Difficulties in the Theory of Transfinite Numbers and Order Types*
  (PLMS s2-4, pp. 29–53, 1907, [DOI](https://doi.org/10.1112/plms/s2-4.1.29)): which collections a
  definition may legitimately form, and cardinality versus order type. Its citation line of
  descent is inventoried in [russell-citation-inventory](../research/russell-citation-inventory.md)
  (376 database-reported citing works, with per-record verification levels).
- Repository [reference notes](../counting-type-inhabitants.md#the-rules-the-solver-implements)
  and [executable examples](../../core/src/test/scala/cardinality/analysis/inhabitation/ReferenceInhabitantsSpec.scala#L27).
- The [evidence register](../research/code-cardinality-foundations.md): for each decision in the
  counting contract, the sources that justify it, how far each was verified, and the boundary
  past which it must not be stretched.

The 27 reference examples are evidence for the supported algebra, not a proof that the Scala
frontend extracts every environment correctly. Ordinary `|B|^|A|` is not a substitute for
analyzing universally quantified signatures. Higher-kinded/Yoneda arguments need their stated
assumptions; they do not provide an automatic solution for arbitrary eo evidence.

Keep mathematical models distinct from runtime representations: a mathematical powerset is not
automatically Scala's finite `Set`, and an idealized terminal top type is not unrestricted Scala
`Any`. Audit the reference notes where they currently overstate frontend support or the safety
of ignoring concrete members.

## 4. Starting point

The following infrastructure exists; its presence does not make the complete frontend sound:

- [Source indexing and type resolution](../../core/src/main/scala/cardinality/compiled/TastyFrontEnd.scala):
  the compiler's symbols and typed trees, read from TASTy (`compiled/Targets.scala` finds and names
  the rows; the scalameta front end with its two passes is gone, docs/plans/compiled-own-types.md).

  captures, alias provenance, and inherited declarations.
- [Inhabitation solver](../../core/src/main/scala/cardinality/analysis/inhabitation/Inhabitation.scala#L5):
  free atoms, products, finite sums, arrow introduction, first-order producers, productivity and
  live-cycle analysis, exact `BigInt` arithmetic with explicit resource limits.
- [Frontend regressions](../../core/src/test/scala/cardinality/analysis/MethodAnalysisSpec.scala#L10):
  selectors, constructors, productive/unproductive cycles, shadowing, aliases, declared slots,
  simple inheritance, and several unsupported-representation guards.
- [Reporting](../../core/src/main/scala/cardinality/reporting/Report.scala#L1) and the
  [sbt plugin](../../plugin/src/main/scala/cardinality/CardinalityPlugin.scala#L15):
  project sources or explicit files/directories/source jars; separate implementation and
  stored-value sections; report artifacts; report-then-fail for unreadable/unparsable inputs.
- Scripted tests cover a project report and a fixture source jar. The baseline-refresh work also
  reruns the full core suite and adds offline derivation/completeness/identity regressions; its
  opt-in runner validates the complete pinned EO archive separately.

The original plugin walking skeleton, basic per-definition reporting, readable sizes, artifact
writing, and report-then-fail work are already present. The remaining effort is primarily counting
correctness, expressiveness, and reproducible real-library validation.

## 6. Milestones, in order

### V1.1 — Establish a reproducible, reviewable baseline

**Status: partial.** The [baseline](../baselines/eo-core-0.16.0.txt) is reproducible with an
opt-in checksum-verifying runner. A method identity/status inventory and a small
[review ledger](../baselines/eo-core-0.16.0-review.md) are retained; reversed-source method results
are checked. Expanding independent review and definition identities remains work.

- Retain the full eo report with the analyzer revision, input coordinate/checksum, Scala/tool
  versions, command, and analysis limits. Use a repository-relative artifact location, not a
  developer-specific cache path.
- Establish stable row identity from source, owner, declaration kind, and signature, including
  overloads. Keep a small review ledger separating emitted counts from independently validated
  counts and unresolved obligations.
- Reconcile historical README/reference claims with the counting contract above.

**Acceptance:** another checkout can reproduce the inventory and report from the pinned source
archive; input-order changes do not change results; every baseline row has a review status.
Report generation and correctness validation remain distinct.

### V1.2 — Close scope and identity gaps before extending the algebra

**Status: partial implementation; soundness work remains.**

Direct override identity now compares contextual parameter clauses, normalizing `using` and
legacy `implicit` spellings while preserving nominal types, method binder identities, and parent
substitutions. Named/anonymous evidence, multiple clauses, genuine contextual overloads, and
unsupported-modifier guards have source-to-count regressions and compiled syntax fixtures.
Ordinary/contextual mismatches with otherwise matching parameter keys, and context-bound
desugaring, are still unsupported. The pinned EO run after this feature has an unchanged report
body and inventories: other scope/type obligations still block its contextual methods. The
retained baseline above remains historical production output; the feature validation is not
a new claim of more resolved EO rows.

Transparent first-order aliases now normalize in direct inherited method signatures, including
qualified and chained aliases and receiver binders captured at their declaration site.
Frame-keyed substitutions prevent a shadowing method binder or a caller's names from changing
the alias meaning; a nearer source declaration or import shadows a farther enclosing binder, and
a qualified selection never resolves to a same-spelled (or backticked) method formal. Distinct
nominal types remain distinct even when their representations agree. Source-to-count regressions
and compiled fixtures cover these boundaries. Recursive/opaque aliases, abstract members, bounded/
higher-kinded alias parameters, and type-lambda aliases remain guarded, and the expansion depth
budget covers nested argument positions, not only body-to-body chains. The pinned EO report body
and inventories are also unchanged after alias normalization.

Package-scoped visibility is now modelled for `private[p]` grants: a declaration granted to an
enclosing package is reachable from its sibling files and from subpackages, while an unqualified
top-level `private`, a `this` or class qualifier, and a `protected[p]` whose subclass condition
this model does not track keep the stricter enclosing-declaration rule. Qualified name lookup
also tries every enclosing-package prefix of the use site, the way nested package clauses
resolve. Import clauses bind their names through the same lookup: named and renamed selectors
resolve or refuse, wildcards bind last, position decides ordering within a block, and an import
whose target is unavailable denies the name to the enclosing packages and the builtin
vocabulary. Source-to-count regressions pin the grant, the subpackage case, the file-private
adversarial case, the representation reason a package-private abstraction carries after
resolution, the named/relative/renamed/wildcard/companion-wildcard import forms, the builtin
refusal, the import order, and the alias-position anchor. The [full-checkout
run](../baselines/eo-checkout-2026-10-27-full.md) moved no row's count: 145 rows then gained
reasons and 26 inherited-override obligations surfaced from package visibility, then 569 rows
gained truthful reasons from import bindings; the pinned 0.16.0 run keeps its five reviewed
counts, its 480-row inventory and its stored-value rows, and its method TSV byte-identical.

Deferred, separate from this change: an adversarial backticked binder colliding with a qualified
selection caused a stack overflow in `MethodProjections` during full measurement. A separate
value-dependent alias example (`type Alias = ev.Out`) stayed unresolved on an abstract
representation rather than exercising the intended override-identity guard. These need isolated
identity tests and resolver-robustness work; neither has an established end-to-end count.

**Attempted and reverted: capability-binder irrelevance.** The candidate rule treated a sibling
capability's method binder as rigid when it occurred in both input and result types. This loses
legal type instantiations. Given `foldMap[M](f: A => M)(s: S): M`, a target with `s: S` can
instantiate `M = A` and call `foldMap[A](identity[A])(s)` to obtain an `A`, even without an
existing `A` value. A supplied capability implemented as `f(extract(s))`, for an available
`extract: S => A`, witnesses this behavior without inventing a constant of an arbitrary type.
The earlier explanation using a uniform `m₀: M` was incorrect. The proposed `Finite(1)` count
for the stripped-down `headOption` example therefore was not established.
The experimental EO run changed no numeric results; its diagnostic buckets shifted from
104 to 18 polymorphic-capability rows and from 183 to 251 unresolved-type rows. Those are
reverted experiment measurements, not the landed baseline. Capability instantiation and
environment completeness must be modeled before erasing these obligations.

The next environment-resolution work follows the
[bounded dependency resolution and caching plan](bounded-dependency-resolution.md).

Extend the existing regressions with focused source-to-count cases for:

- Declaration identity across files and overloads. The current
  [self-exclusion check](../../core/src/main/scala/cardinality/analysis/Measurement.scala#L224) compares source offsets;
  equal offsets in different files must not identify the same declaration.

  parent or resolve an ambiguous parent by taking the first match.
- Method-owned type binders in declared polymorphic capabilities, method-body versus signature
  scopes, term/type namespace collisions, and shadowed-but-qualified receiver fields.
- Imports/exports, including wildcards and renames; companions and nested modules sharing class
  binders; relevant receiver capabilities outside the immediate lexical chain.
  **Partial:** named, renamed and wildcard imports now bind through lookup — anchored at every
  enclosing package prefix, `_root_` stripped, position-ordered, refusing the builtins they
  shadow — and reconstructed alias bodies inherit the declaring scope's import binding. `export`

  The [full-checkout ledger](../baselines/eo-checkout-2026-10-27-full.md) records the measured

## 10. Future exploration: HyperLogLog measurement

**Status: deferred exploration, outside v1's correctness engine and completion criteria.**

Reference: Otmar Ertl, *New cardinality estimation algorithms for HyperLogLog sketches* (2017),
[paper](https://oertl.github.io/hyperloglog-sketch-estimation-paper/paper/paper.pdf). It develops
corrected and maximum-likelihood estimators, including joint estimation of intersections,
relative complements, and unions from two sketches.

Potential uses:

- **Bounded implementation enumeration:** estimate the distinct canonical constructions generated
  within a declared search budget when retaining an exact set becomes too expensive.
- **Observed runtime diversity:** an explicitly opt-in, separate measurement of distinct values
  produced by a workload, compared with the statically permitted state space.
- **Overlap experiments:** estimate overlap between large generated sets of constructions from
  different capabilities. Ertl's joint estimator is relevant here; tagged sum constructors
  remain distinct and must not be treated as an untagged set union.

Prerequisites and limits:

- Define element identity and supported normalization before hashing. HLL cannot discover
  observational equivalence, repair an incomplete scope, or enumerate inhabitants for us.
- Sketching reduces memory for counting a supplied stream, not the cost of generating that stream.
  Prototype only when an actual workload justifies it; small sets should remain exact.
- Label estimates separately from exact implementation counts and stored-value estimates.
  Record sketch precision/error, hash configuration, and enumeration bounds or workload coverage.
  Sketch error does not account for inhabitants that were never generated or observed.
- A finite sketch cannot prove `ω`, completeness, or impossibility. An estimate must not replace
  an unresolved static answer or be presented as a rigorous bound on the full inhabitant set.
- Validate any prototype against exact counts on tractable cases before using it on larger ones.

### What landed after the decisions

The decisions below were taken on analyzer `55f6ea1`, which read sources with scalameta and

- **The TASTy front end is the only one** (D1 there; rule T in §2). The analyzer reads the

  refused; reading uncompiled sources is future work.
- **Templates are the compiler's symbols.** A parent is the class the compiler resolved, and two
  classes of one simple name in different packages are two templates. The open-world overcount of

- **Measurement tools.** `scripts/build-corpus.sh` builds a corpus from one published artifact

- **Toolchain.** core is on Scala 3.10.1 with tasty-query 1.10.0, which reads Scala 3.0 to 3.10.
- **A new class of `?`: `not read from compiled classes yet: <reading>`.** It marks a reading the
  TASTy front end has not taken over. It is "not implemented yet" by name, so it is never a final
  refusal. A row prints its first such reason only: another reason may stand behind it.
- **Model rulings that move eo rows.** D5: a construction that throws builds no value and is not
  refused. D6: re-entry among a capability record's members through another instance is counted;
  only same-instance re-entry refuses. Recursive stored definitions are solved by a fixed point,
  and a lazy cycle's arms count at their ν value.
- **Old numbers were wrong in places.** The front-end comparison corrected 85 method rows and set
  70 aside as resting on an unsound re-entry rule (`corrected.txt`, `old-unsound.txt` under

A method, constructor or definition row is done when it is either

1. a number that passes the validation bar below, or
2. a `?` whose every reason is on the final-refusal list.

eo is fully measured when every row of every module in scope is done. No row may be left with a
reason that means "not implemented yet" (every `not read from compiled classes yet` row is one),
and a resource limit is never a final refusal.
