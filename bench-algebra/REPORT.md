# Symbolic algebra evaluation: Symja vs Rings vs the model carrier vs this library

**Question.** The ωⁿ tier in [issue #39](https://github.com/Constructive-Programming/scala-cardinality/issues/39)
can be written as a four-coordinate carrier `aε₀ + bωⁿ + cω + d`. The analyzer never solves a
cardinality expression to a numerical value; it performs exactly two operations on it —
decides the model's order on two expressions (`<`, `=`, `>`), and renders the reporting
projection `aε₀ + bωⁿ + cω + d`. Before building the tier, should either operation be
delegated to a symbolic library so that expressions such as `(1+ω)^N` stay factored?

**Answer: no — build the four-coordinate carrier itself.** It is implemented in this
evaluation (`ModelAlgebra`, 92 physical lines, no dependency) and is the only backend that
answers all twelve corpus cases exactly per the model, including ω and ε₀ in the exponent:
a huge finite power costs logarithmic work and never expands, an infinite exponent reaches
the ε₀ coordinate, and ε₀ does not absorb (`ε₀ + 1` stays above `ε₀`). It is also the
fastest backend on both use cases. Rings handles every finite-degree polynomial and refuses
the moment the exponent stops being a small constant; Symja refuses most comparisons beyond
that point and **silently returns impossible projections** (`-1 P + 1 w + 1`) for polynomial
exponents.

Measured data: `results/summary.md` (generated by `summarize.py`), raw JMH
`results/jmh.json`, correctness in `results/correctness.txt`, stress probes in
`results/stress-corpus.log`, `results/stress-huge.log`, `results/stress-symbolic.log` and
`results/stress-boundary.log`. Commands are in [README.md](README.md).

## The corpus

Twelve expressions, each tied to the Scala shape that gives rise to it (`w` stands for ω);
powers take their exponent as a value, because a function space raises the codomain to the
domain's cardinality and that domain can itself be a polynomial:

| Case | Shape | Expression | Model projection |
| --- | --- | --- | --- |
| eitherStrings | `Either[String, String]` | `w + w` | `2ω` |
| optionString | `Option[String]` | `w + 1` | `ω + 1` |
| pairStrings | `(String, String)` | `w·w` | `ωⁿ` |
| pairOptions | `(Option[String], Option[String])` | `(1+w)^2` | `ωⁿ + 2ω + 1` |
| tripleOptions | triple of `Option[String]` | `(1+w)^3` | `4ωⁿ + 3ω + 1` |
| booleanOption | `(Boolean, Option[String])` | `2·(1+w)` | `2ω + 2` |
| eitherStringPair | `Either[String, (String, String)]` | `w^2 + w` | `ωⁿ + ω` |
| optionEither | `(Option[String], Either[Boolean, String])` | `(1+w)·(2+w)` | `ωⁿ + 3ω + 2` |
| intToString | `Int => String` | `w^(2^32)` | `ωⁿ` |
| optionDomain | `Option[String] => String` | `w^(1+w)` | `ε₀` |
| eitherDomain | `Either[String, (String, String)] => String` | `w^(w^2+w)` | `ε₀` |
| stringToString | `String => String` | `w^w` | `ε₀` |

The first eight are polynomials a materialized carrier can hold. The last four put ω in the
exponent — a huge finite exponent, two polynomial exponents and an infinite one. This is not
an exotic corner: any function type over an infinite domain lands there, and `Int => String`
already needs `w^(2^32)`.

## The model carrier

`ModelAlgebra` is the four-coordinate carrier issue #39 plans, written for this evaluation:
`a·ε₀ + b·ωⁿ + c·ω + d` with exact BigInt coefficients. Multiplication is bilinear over the
tier table (ω·ω = P, ω·P = P·P = P, anything with ε₀ is ε₀), so coefficients multiply and
every contribution lands in its output tier: `2ω·3ω = 6P` and `(P + ω)·ω = 2P`. Finite powers
use repeated squaring on the four coordinates — which is why `w^(2^32)` costs 32 bilinear
steps and `(1+w)^(2^32)` is just as cheap, where Symja refuses and Rings cannot even hold
the input. Infinite exponents follow the model's conventions: an infinite base reaches ε₀,
a finite base above one stays ω (matching current `Size.pow`). ε₀ does not absorb:
`ε₀ + 1 > ε₀`, and comparisons are lexicographic in `(a, b, c, d)`.

One deliberate information loss, per the contract's chosen convention: `ωⁿ` is a single
tier, so `w^(2^32)` compares equal to `w^2` — exact polynomial carriers order them apart.
`Verify` pins this as expected behavior, not an accident.

## Use case 1: comparison

Seven pairs with independently derived signs, including `2w < w^2` — the ordering this
evaluation exists to check — and `(1+w)^2 = w^2 + 2w + 1` with the left side factored.
Microseconds/op:

| Pair (expected) | Symja | Rings | model | current Size |
| --- | ---: | ---: | ---: | ---: |
| eitherBelowPair (<) | 2.48 | 0.0012 | 0.0013 | 0.0021 |
| pairBelowSumOfPowers (<) | 10.69 | 0.206 | 0.0019 | 0.0026 |
| sumBelowCube (<) | 5.28 | 0.0013 | 0.0014 | 0.0025 |
| eitherPairBelowOptionPair (<) | 12.82 | 0.150 | 0.0016 | 0.0023 |
| optionBelowBooleanOption (<) | 10.91 | 0.146 | 0.0017 | 0.0043 |
| mixedAboveOptionPair (>) | 23.70 | 0.292 | 0.0017 | 0.0024 |
| squaredEqualsExpansion (=) | 31.49 | 0.310 | 0.0018 | 0.0016 |

Symja, Rings and the model carrier return all seven correct signs. Current `Size` gets
**zero of seven**: it orders `2ω` above `ω` (so `Either[String,String] > (String,String)`,
the original complaint), collapses `w^2` and `(1+w)^2` and `(1+w)^3` all to `ω` (equal), and
orders `w^2 + w` above `ω` where the exact order says below. Its signs are recorded in
`results/correctness.txt`. `Size.mul` collapses `2·ω` to `ω`; that is the degree and
coefficient information the ωⁿ tier exists to carry.

The model carrier's comparisons are four BigInt comparisons with no allocation — it is the
fastest backend, ahead of even the coarse `Size` on most pairs. Rings walks stored
coefficients downward; Symja answers each degree and coefficient through
`Exponent`/`Coefficient` queries.

| eitherStrings | 2.03 | 0.048 | 0.009 | 0.118 |
| optionString | 1.80 | 0.089 | 0.010 | 0.096 |
| pairStrings | 4.35 | 0.102 | 0.013 | 0.066 |
| pairOptions | 6.29 | 0.176 | 0.013 | 0.056 |
| tripleOptions | 7.23 | 0.254 | 0.018 | 0.040 |
| booleanOption | 4.41 | 0.125 | 0.019 | 0.044 |
| eitherStringPair | 7.55 | 0.135 | 0.012 | 0.058 |
| optionEither | 5.95 | 0.193 | 0.030 | 0.052 |

## The beyond-polynomial cases

`Verify` classifies each backend's answer as exact, refused, or silently wrong; a backend
may refuse a case it cannot decide, but must not answer wrong:

| Case | Symja | Rings | model | current Size |
| --- | --- | --- | --- | --- |
| intToString (`w^(2^32)`) | `1 P + 0 w + 0` — exact | construction refused | **`1 P + 0 w + 0` — exact** | `ω` — coarse |
| optionDomain (`w^(1+w)`) | **`-1 P + 1 w + 1` — silently wrong** | construction refused | **`ε₀` — exact** | `ε₀` — exact |
| eitherDomain (`w^(w^2+w)`) | **`-1 P + 1 w + 1` — silently wrong** | construction refused | **`ε₀` — exact** | `ε₀` — exact |
| stringToString (`w^w`) | **`-1 P + 1 w + 1` — silently wrong** | construction refused | **`ε₀` — exact** | `ε₀` — exact |

- **The model carrier** answers all four exactly: `w^(2^32)` is one ωⁿ unit (square-multiply
  on four coordinates, 32 steps), and the infinite exponents land in the ε₀ coordinate. It
  also compares them: ε₀ outranks `w^2`, every beyond case stays below itself plus one, and
  `w^(2^32)` equals `w^2` — the tier collapse, pinned as expected in `Verify`.
- **Rings** refuses at construction: `Int` degree cannot hold `2^32`, and a polynomial
  exponent is not a constant at all. Honest and immediate.
- **Symja** holds all four compactly (3–7 leaves) but its projection substitutes `w = 1`,
  which turns `w^(1+w)` into `1^2 = 1` and manufactures `-1 P + 1 w + 1` — a negative
  coefficient, impossible for a cardinality, for all three ε₀ cases. Its `intToString`
  answer is right by the same accident. This is the worst failure mode available: a
  plausible-looking wrong count with no error.
- **Current `Size`** answers all four, three correctly (its power rules already encode the
  model's exponent conventions), and renders `ω` for `Int => String` — precisely the
  missing tier.

`Stress` (`results/stress-corpus.log`) probes the same cases through Symja's comparison:
`compare(w^(2^32), w^2)` answers `+1` correctly (a plain monomial's degree survives), while
the polynomial-exponent comparisons refuse honestly (`not an integer: 1+w`) — the same
expressions whose projections answer wrong.

## Correctness beyond the corpus

The boundary ladder (`results/stress-boundary.log`) locates Symja's query limit at degree
`2^20` (iteration limit), with unevaluated forms at `Int.MaxValue`; the `huge` and
`symbolic` probes show a comparison of `(1+w)^4294967296` against `p + w` answered `-1`
through collapsed degrees (0 vs 1) — right by accident — while every other query refuses.
The adapter decodes nothing to `0`: a query that stays symbolic throws. Earlier versions of
this evaluation decoded those refusals through `toIntDefault()` — silent wrong answers,
worse than a refusal.

Symja's defaults also disagree with the contract where it assigns explicit values: `0^0`
evaluates to `Indeterminate` (the contract needs `b^0 = 1`) and `ω^ω` stays unevaluated (the
contract needs ε₀ — the model carrier computes it). `Natural` keeps huge finite powers exact
and compact (`2^65537` in 3 nodes) and is the fastest backend in the `finitePower`
measurements; the model carrier materializes its coefficients as BigInt and will hand that
job to `Natural` in the analyzer.

## Lines of code and ease of use

| Source | Physical lines | Code lines |
| --- | ---: | ---: |
| `ModelAlgebra.scala` (the #39 carrier) | 92 | 66 |
| `RingsAlgebra.scala` | 48 | 36 |
| `SymjaAlgebra.scala` | 49 | 37 |
| `CurrentAlgebra.scala` | 20 | 13 |
| `Algebra.scala` (shared glue + corpus) | 131 | 87 |
| `Verify.scala` (incl. `Stress`) | 213 | 176 |
| bench classes (`Construct`/`Compare`/`Project`/`Finite`) | 180 | 134 |

The adapters are small because the shared trait hides the API differences; the differences
are the ease-of-use cost:

- **model**: four BigInt coordinates, one bilinear multiply, one square-multiply power, one
  lexicographic compare, one render. No representation limits, no refusals on the corpus,
  no hazards found.
- **Symja**: `IExpr` trees built with `F.Plus`/`F.Times`/`F.Power`, evaluated by an
  `ExprEvaluator` (one per thread, history disabled). Query results must be decoded
  defensively — the natural `toIntDefault()` turns every refusal into `0`, and the
  substitution route manufactures wrong projections with no error at all.
- **Rings**: `UnivariatePolynomial[BigInteger]`, mutable operations, `clone()` before every
  `add`/`multiply`, `Int` degree, coefficients always materialized, constant exponents only.
- **current `Size`**: a case class with finite/ω/ε₀ coordinates; correct order and
  projection for the tier it has, wrong for the degrees it collapses — but already the only
  pre-existing backend that answers the ε₀ cases, and correctly.

Dependency weight (coursier resolution):

| Library | Artifacts | Total jar size |
| --- | ---: | ---: |
| `org.matheclipse:matheclipse-core:3.2.0` | 57 | 39.6 MiB |
| `cc.redberry:rings:2.5.5` | 5 | 5.0 MiB |
| model carrier | 0 | 0 |

Symja pulls Log4j, Jackson, Hipparchus, JGraphT and more. Both libraries are JVM-only;
`core` is also compiled for Native (`core-native`), so a production dependency would need
platform separation, not just a version bump.

## Self-measurement by this library

`Verify self` measures the shared algebra and adapters with sources only: 62 signatures,
4 finite, 20 countably infinite, 38 unresolved. `DependencyMeasure` adds 262 compiled
dependency stubs: 42 signatures, 4 finite, 20 countably infinite, 18 unresolved, no analyzer
errors. The model adapter resolves completely (constructor 1, methods ω); the Symja and
Rings adapters refuse because `IExpr` inherits `edu.jas.structure.GcdRingElem` and Rings'
`BigInteger` inherits `java.lang.Number`, neither supplied. This measures exposed
implementation choices under the closed-world contract; it is not a runtime-complexity
score, and `?` does not mean high cardinality.

## Decision

1. Implement #39 as the four-coordinate carrier — `ModelAlgebra` in this evaluation is the
   working prototype: 92 lines, fastest on both use cases, the only backend answering all
   twelve corpus cases exactly per the model, ω and ε₀ in the exponent included. Share the
   tier rules between `Size` and `Card` without sharing rounding; keep coefficients symbolic
   through `Natural` where the analyzer needs it.
2. Do not delegate comparison or projection to a CAS. Rings stops at constant `Int`
   exponents; Symja's answers beyond that are either refusals, accidents, or silently wrong
   projections with impossible coefficients.
3. Track multiplicative-depth growth in the solver (for the ε₀ promotion rule), not in a
   polynomial representation. Collapsing all finite powers means the carrier cannot
   distinguish `ω²` from `ω⁴`; a solver-local counter can.
4. Keep this evaluation module isolated and unpublished. It is evidence for this decision,
   not a production path.
